# Application Security Roles

Application security roles share one purpose: to ensure the software an organization builds and operates is designed, written, and delivered with security in mind. Rather than testing systems from the outside after they exist, these professionals work close to the development process, helping teams keep weaknesses out of the code and lowering the cost of fixing those that slip through. Their value comes from shaping how software is made, not only from inspecting the finished result.

## What these roles share

- A place close to engineering teams rather than outside them, intervening before software ships.
- A focus on prevention: secure defaults, reusable patterns, and early review that stop whole classes of weakness.
- Influence over authority, since practitioners rarely own the code and must persuade teams to act.
- Fluid boundaries, so many people move between these roles as team size, technology, and maturity change.

## Roles

- [Application Security Engineer](application-security-engineer.md): a broad specialist who helps development teams find and remediate weaknesses across the lifecycle, combining analysis, tooling, and guidance.
- [Secure Code Reviewer](secure-code-reviewer.md): examines source code, manually or with supporting tools, to find flaws in logic, data handling, and trust boundaries before they reach production.
- [Product Security Engineer](product-security-engineer.md): takes a product-centered view, embedding security into the design decisions and ongoing roadmap of a specific team or product line.
- [DevSecOps Engineer](devsecops-engineer.md): integrates security controls and automated checks into continuous integration and delivery pipelines so testing and policy enforcement happen as a natural part of shipping.
- [Security Champion](security-champion.md): a developer embedded within an engineering team who advocates for secure practices and connects the team to the broader security function.
